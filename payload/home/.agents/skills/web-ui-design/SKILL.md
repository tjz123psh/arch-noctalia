# Web UI Design

端到端 Web 界面 skill：判断 → 分流 → 验收 → 跨端边界。开始前先读完第 1 段并给出结论，再按第 2 段只读命中的那一篇 reference，最后按第 3 段选风险档收集真实证据。不要求读完所有 reference；判断标准全部在第 1 段内。

## 工作流

1. **判断**（第 1 段）：产品类型、已知/推断/未知、一句话问题、内容模型与信息几何、分组、卡片准入、密度、动效动机、表单校验时机——逐项给结论
2. **UI Contract**：结构决定后、实现前把决定写成一句话加最小模板（见 `references/ui-contract.md`）；短任务直接写进对话，长任务落到项目根的 `DESIGN.md`
3. **分流**（第 2 段）：按判定信号读一到三篇 reference，不追求全读
4. **实现**：跟随项目现有架构、命名与测试；小步可回滚；只为明确的复杂度新增抽象或依赖；保持公共 API 与配置默认兼容
5. **视觉闭环**：真实渲染 → 截图 → 自评 → 修正 → 再截图（视觉变化时必须走完）
6. **验收**（第 3 段）：选 Smoke / Standard / Release，逐维度留证据，写出残余风险

范围窄的评审（单个页面、单个断点问题、一次对比度修复）可从第 2 段直接开始，但仍要给出第 1 段中与本次改动相关的判断结论，并按第 3 段留证据。

## 1. 判断

按顺序走完，每项都要有结论，不能留空。

### 产品类型

| 类型 | 信号 | 主导取向 |
|---|---|---|
| 工具 / 仪表盘 / 后台 | 高频重复、要比较、要批量、内部或专业用户 | 扫描效率优先：密度、对齐、快捷键、状态完整；装饰克制 |
| 展示 / 落地页 / 产品站 | 首次印象、说服、讲清一件事 | 单一主张 + 一条主路径；层次与排版承担说服 |
| 品牌 / 沉浸表达 | 视觉本身是产品的一部分、作品集、活动页 | 视觉立场先行，签名元素 + 环境质感；可用性底线不变 |
| 文档 / 参考站点 | 内容来自多页资料、要能检索与定位 | 信息架构与可达性优先：导航、搜索、无孤儿视图；不编造内容 |

同一页面可混合，但每个视图只有一个主导取向。"现代美观 / 高级 / 有质感"是加分维度，不改变主导取向，也不该被当成放宽可用性的理由。

### 已知 / 推断 / 未知

- **已知**：来自需求、代码、数据、现有产品中可查证的事实
- **推断**：为继续工作而作的最小假设；写清依据、保持可逆
- **未知**：会改变结构或流程的问题；能从项目查就先查，只有高影响且不可恢复时才问用户

不要虚构用户研究、业务指标、品牌历史或"用户喜欢"。没有真实内容时用贴近领域的示例，并明确标为占位内容。改现有产品时先找出其视觉语言与已学会的交互约定，保留有效身份。

### 一句话问题定义

判断的可见产物是一句话：

> 为 `[谁]` 在 `[什么环境]` 完成 `[首要任务]`，界面需要突出 `[内容/操作]`，成功表现为 `[可观察结果]`。

再确认六个变量：使用频率、熟练度、紧迫性、错误代价、内容密度、设备与输入方式。专业高频工具与低频消费页面不能用同一套简化逻辑。

### 内容模型与信息几何

先列真实对象、属性、动作和状态（正常 / 加载 / 空 / 错误 / 离线 / 无权限 / 部分数据 / 极端内容），再选结构：

| 内容关系 | 优先结构 |
|---|---|
| 连续阅读、论述、说明 | 文档流、章节、宽窄栏交替 |
| 同类对象快速扫描 | 列表、紧凑行、分组索引、feed |
| 多属性比较 | 表格、矩阵、对齐标尺 |
| 浏览后查看详情 | 主从视图、列表—详情、Miller 列 |
| 创建或直接操纵对象 | 画布 + 检查器、舞台 + 工具带 |
| 时间、版本、过程 | 时间线、轨道、步骤流、事件日志 |
| 空间或位置关系 | 地图、平面、节点图、空间叠层 |
| 状态推进或责任流转 | 看板、泳道、队列 |
| 深层层级 | 树、目录、outline、逐级钻取 |
| 少量重点内容的沉浸表达 | 舞台、蒙太奇、叙事滚动 |
| 多源监控与告警 | 分区仪表盘、主指标 + 明细流 |
| 输入与决策 | 单页表单、分组表单、向导、分支流程 |
| 高频命令与批量操作 | 命令面、工具栏、快捷键层、批处理表格 |

结构必须对应真实关系；可以混合结构，但关系没变就不要为"有层次"换布局。默认避免"Hero + 卡片网格"和"侧栏 + 仪表盘"这类条件反射，也避免给所有内容加容器、编号或装饰。

### 分组：留白还是容器（Gestalt）

按最轻手段优先，逐级升级：

1. **邻近律（默认）**：组内间距 < 组间间距。标签贴紧它的输入框，区块标题离下方内容比离上一节更近；永远不要用边框做留白就能做的事
2. **共同区域**：只有当边界本身有意义时（对象可独立选择、移动、复用，或异质内容需要隔离）才加容器。用能完成任务的最弱容器：背景 > 边框 > 卡片面；嵌套不超过两层；分组边界在低对比度和暗色下仍要成立
3. **隔离效应**：只让少数元素与周围形成差异（一行 ghost 按钮里唯一的 filled 主按钮）；同时高亮多个会互相抵消，且不能只靠颜色

### 卡片准入测试

卡片不是中性容器。仅当对象边界本身有意义——对象可独立操作、移动、选择、复用，或异质内容确实需要隔离——才用卡片。**去掉圆角、阴影和背景后信息关系仍更清楚，就不需要卡片。**

优先尝试这些替代方式：留白与对齐、分节、细分隔线、背景带、列表行、表格、主从面板、连续画布、排版层级。默认避免嵌套卡片，只有内外边界分别表达不同对象、所有权、交互范围或层级，且嵌套确实改善扫描时才保留；避免同尺寸"图标 + 标题 + 两行文案"重复铺满页面。把卡片网格换成 Bento 不算解决了问题——先改信息结构。

### 密度

按使用频率与任务定一档并全系统一致：**Compact**（数据密集表格/仪表盘，每档间距减一级）/ **Comfortable**（默认）/ **Spacious**（阅读型页面，每档加一级）。密度是整体平移，不是个别元素加 padding；相关项小间距、不同区块大间距。仪表盘类界面的默认错误是过疏而不是过密。

### 动效动机

先默认不动，逐条论证再加。三问全答不上来的就是装饰，删掉：

- 它解释了哪个状态变化、空间关系或因果反馈？
- 去掉它，用户是否会失去对界面的理解或掌控感？
- 它是否复用界面已有的空间逻辑（从来源处进、回来源处出）？

入场动画只播一次，且必须贴合被揭示的内容——给每个区块套同一条淡入上移是最强的 AI 味信号。展示/品牌/沉浸型界面还需要静止态"活着"（低振幅、4–12s 周期的环境微动）；但静态内容页不加氛围动效也是正确决定。时长取"移动距离与元素尺寸"决定：即时反馈 ≤100ms、小状态变化 150–200ms、局部转场 200–300ms、全屏转场 300–400ms；进场用 ease-out、退场用 ease-in；只动 transform/opacity，reduced-motion 下必须有可见可用的替代。参数细节见 `references/visual.md`。

### 表单校验时机

| 时机 | 用在哪 |
|---|---|
| onBlur | 首次格式校验（邮箱、URL、电话）——用户已结束输入，不打断思维 |
| onChange（该字段已报错后） | 用户修正时给即时确认 |
| onChange + 300–500ms debounce + `AbortController` | 密码强度、用户名可用性等异步校验 |
| onSubmit | 必填项首次检查；提交时校验全部字段并把焦点移到第一个错误 |

不要禁用提交按钮等表单"合法"（用户不知道错在哪）；不要每次按键都校验；错误放在字段下方而不是 tooltip（触摸/键盘不可达）；错误时保留已填内容；异步校验要有 loading 状态。字段内联 + 长表单摘要 + 系统级错误横幅的三通道分发，以及 10 个以上字段时的分组与进度指示，见 `references/components.md`。

### 响应式是重组

不要把桌面稿等比缩小，也不要默认把所有列纵向堆叠。对每个宽度状态明确：什么必须持续可见、什么可以合并或移入抽屉、比较关系在窄屏如何保留、主操作如何保持可达、密度与导航如何变化。断点依据是**内容开始失效的位置**，设备宽度只作为测试样本。

### 方向发散与设计立场

新项目或结构不明确时，先提出 2–3 个**结构上不同**的方向——改变阅读路径、密度、导航或操作位置，而不只是换颜色、字体和圆角。用六个维度比较并记录为什么选它、为什么放弃其余：首要任务完成速度、扫描与比较效率、内容增长后的稳定性、平台与输入方式适配、无障碍与极端状态、品牌辨识度与实现成本。现有产品、明确 brief 或成熟设计系统已给出结构时，不要强行发散。

结构定下来后写一句设计立场，再定 token：

> `[特质]`，通过 `[结构/排版/色彩/动效手段]` 服务 `[用户任务]`，避免 `[不适合该产品的气质]`。

风格名称不是推理：说"高级、现代、极简、赛博"不等于作出决定，每个形容词都要落到可观察的结构或行为。UI Contract 的最小模板、设计坐标轴与更多要求见 `references/ui-contract.md`。

## 3. 验收证据表

验收在本 skill 内闭环，不串联外部测试 skill。按风险选一档；每个"通过"必须对应证据（截图、控制台日志、DOM/无障碍树断言或自动化测试），口头结论不算。工具失败不是跳过该维度的理由——换手段（新会话、CDP、CLI）或明确写"未验证"并列入残余风险，不得静默跳过。

| 维度 | 小改（Smoke） | 常规（Standard，新建/改版默认） | 发布（Release） |
|---|---|---|---|
| 构建 / 启动 | 必须 | 必须 | 必须 |
| 视口 | 1 窄 + 1 宽 | 375 / 768 / 1440 | 再加 1024、超宽（≥1920） |
| 控制台 | 无相关报错 | 无未处理错误与警告 | 同左 + 无失败网络请求 |
| 断点边界 | 无横向溢出 | 断点切换处无跳变、遮挡、重叠 | resize、字体放大、主题切换后仍不破 |
| 键盘可达 | — | 主流程纯键盘走通；Tab 序 = 视觉序；焦点可见 | + 模态焦点陷阱、关闭后回到触发元素、Esc 关闭 |
| 对比度 | — | 正文 ≥4.5:1；大字与 UI 元件 ≥3:1 | + 强制高对比、200% 缩放 |
| 状态 | — | 一个适用的失败/空/加载态 | + 离线、无权限、空结果、慢网、bfcache |
| 主题 | — | 产品支持时覆盖明/暗 | + 强制高对比 |
| 动效 / 性能 | — | reduced-motion 下入场与氛围动效冻结或降级 | + 60fps、CLS、长列表与内存/监听器清理 |
| 视觉闭环 | 改动可见时：真实截图 → 评审 → 修正 → 再截图 | 同左（必须） | 同左 + 逐屏评审每一屏 |
| 反模式检测 | — | 跑 `detect.mjs --json <文件或目录>`；命中项逐条确认或书面豁免 | 同左 + 全部 `warning` 已修复或已记录豁免理由 |
| 韧性 | — | 极端输入（超长/空/Emoji/CJK）与一个失败态的恢复路径 | 同左 + 断网/慢网/429/5xx、并发与重复提交、无权限与只读 |

### 视觉闭环就是自我评审

视觉变化时必须走完：**真实渲染 → 截图 → 逐屏自评 → 修正 → 再截图**。构建通过、DOM 断言和控制台干净都不能替代这一步。自评按 `references/critique.md` 的切面挑一到三项（按本屏主要风险选：层次、排版、色彩、构图、可供性、信息密度、品牌一致性），每项给出"观察—问题—修复"并评级 `pass` / `minor issue` / `major issue`，最后按 `major` 优先修。每次修正后重新截图复核，改完再判。

自评不看风格偏好，只看行为错误、回归、可访问性缺口与任务阻塞；每条修复落到可观察的结构或数值。发现的问题若推翻了 UI Contract 里的决定，同时更新 Contract 并记录取舍。

### 实现后九项检查

1. **任务**：首要任务是否无需解释就能开始
2. **结构**：去掉颜色、圆角、阴影后，层级是否仍清楚
3. **布局**：容器边界是否都有语义？卡片能否被更简单结构替代
4. **内容**：长标题、空数据、错误、加载、权限和大量数据是否成立
5. **交互**：焦点、键盘、触摸、撤销、反馈和危险操作是否完整
6. **响应式**：窄、中、宽是合理重组，而非压缩或堆叠
7. **身份**：隐去 logo 后，它是否仍像这个产品而不是同类模板
8. **克制**：删除一个装饰或容器后是否更清楚？是则删
9. **表现力**：是否有一处值得记住的视觉主张？通篇平淡、无氛围、无生命力同样是没完成任务

克制与表现力是同一判断的两端：删掉不服务内容的噪声，也要为服务内容的表达留足力度。高密度工具或已有系统界面可以用更安静的语言，只要层级、任务和身份清楚；展示/品牌/沉浸型界面若只有纯色平背景、系统字体和一次性入场，通常尚未形成足够的表达。

### 防过度与防平淡自检

**减法一侧**：能否原样换到另一个行业？是否因为"看起来像设计"而加卡片、渐变、玻璃、巨型数字、胶囊、插画或动效？是否把"不要常见模板"误解成随机、不一致或故意反常？是否用伪精确数据、虚构奖项、空泛营销文案填补内容？是否只做了理想状态而遗漏真实状态与长内容？是否尊重现有系统而无授权重新品牌化？

**加法一侧**：排版有没有真正的层级张力与字形气质，展示标题的骨架、笔画对比、曲线、节奏是否匹配画面且中英文字形已真实渲染验证？背景是不是一块死色，氛围（渐变纵深、颗粒纹理、极慢光影、近黑而非纯黑）是否与主题匹配地在场？界面静止时是活的还是死的？有没有一个与主题相关的签名视觉时刻？展示/品牌/沉浸任务是否误用了产品工具的克制标准？

两侧要同时通过：只满足减法是保守，只满足加法是炫技。重要结构和视觉选择都应可追溯至用户、内容、平台或品牌证据。

### 关键检查怎么执行

- **横向溢出**（每个视口都跑）：`document.documentElement.scrollWidth` 不得超过视口宽；逐个排查图片、表格、代码块、长 URL、不换行标题，以及 sticky/fixed 元素是否遮挡内容或互相重叠
- **键盘**：只用 Tab / Shift+Tab / Enter / Space / Esc / 方向键走主流程；确认焦点环可见、焦点不被 sticky 头遮挡、关闭浮层后焦点回到触发元素
- **对比度**：用浏览器 DevTools 或 WebAIM 实测正文、大字、UI 元件与焦点环，不用目测
- **状态**：用真实长内容、CJK 与长翻译填充，而不是 lorem ipsum
- **性能**：看首屏可交互时间、滚动与输入是否掉帧、卸载后监听器是否清理

报告列出：视口、主题、字号、输入方式、状态、步骤、证据、期望、实际、残余风险。未运行的维度必须写明；空白不等于通过。完整矩阵与平台注意点见 `references/validation.md`。

## 4. 跨端边界

- **Do NOT** 用于原生移动端（iOS/Android/Expo 界面）→ 用 `mobile-design`，含其验收段。
- **Do NOT** 用于交互式终端、CLI 全屏界面、TUI → 用 `tui-design`，含其验收段。
- **Do NOT** 用于非视觉逻辑或纯后端改动；单个已确定的样式值、明确 UI bug 的修复，可跳过第 1 段完整判断但仍按第 3 段收证据。
- 品牌视觉主导的站点（落地页、活动页、作品集）**不是排除项**：视觉立场、签名元素与质感标准都在本 skill 内（`references/visual.md`）。
- 原生桌面（GTK/Qt/WinUI/Tauri）没有对应的平台 skill：结构用本项目约定加本 skill 第 1 段的判断标准推导，只有内容真正渲染在浏览器里时才用本 skill 的验收矩阵。Tauri 这类双平台栈：桌面窗口与系统行为归桌面侧，WebView 内容归本 skill。
- 结构与信息几何的推导、UI Contract、逐屏视觉评审、文档站生成都是本 skill 自带能力，分别在 `references/ui-contract.md`、`references/critique.md`、`references/doc-site.md`；浏览器取证与单文件交付物在 `references/validation.md` 与 `references/artifacts.md`。不要引用本 skill 之外的同类能力。
- 交付后如发现 HTML 结构与内容需要重新规划，回到第 1 段重走判断，而不是在同一份实现上继续叠补丁。
