# UI Contract

UI Contract 是一次界面任务从结构决定到验收证据的**单一交接物**。它记录已作出的决定和可观察的成功条件，不是需求复述、情绪板，也不替代设计系统的 token source。实现、截图评审和验收都以同一份 Contract 为准。

## 何时建立与保存

- 新建、重设计或宽泛视觉需求：结构决定后、实现前建立
- 单个明确样式值、局部已复现的 UI bug、纯非视觉逻辑：不必为了流程补 Contract
- 短任务：直接写进对话，保持在 8 行内，并在压缩上下文时把它原文带进摘要（agent 输出的 `<protect>` 不跨压缩保留）；长期、跨回合或跨多人任务：在项目根创建或更新 `DESIGN.md`
- 既有项目已有设计系统、产品 brief 或设计文件时，**链接**权威来源（token 定义见 `design-system.md`），不要复制出第二套 token、内容或产品事实

## 最小模板

```text
产品：谁在何种环境完成什么首要任务；成功的可观察结果。
结构：信息关系、导航/阅读路径与主操作位置。
视觉立场：场景气质、一个服务任务的记忆点，以及避免的失配语气。
令牌：颜色使用比例、已验证的字体/字形 fallback、间距、形状与动效边界。
状态：本产品实际适用的加载、空、错误、权限、离线、长内容或极端数据。
响应式：窄/中/宽中持续可见、合并或按需显示的内容；主操作如何可达。
验收：视觉风险、主流程、适用视口/窗口状态、Smoke/Standard/Release 和证据。
```

## 使用纪律

1. 每行只写能指导实现或验证的决定；未知项标为待验证，不虚构研究、品牌历史或产品状态
2. 视觉复核发现问题时修正实现；若问题**推翻了原决定**，同时更新 Contract 并记录取舍
3. Contract 的"避免项"是该 brief 的风险提示，不是跨产品禁令——卡片、暗色、动效、渐变或居中内容都可以成立，但要能说明它表达的对象关系、平台惯例或视觉立场
4. 验收只覆盖产品承诺的状态与输入方式；没有数据、网络或权限语义的静态页面不要伪造对应状态
5. 交接给设计文件、组件库或代码时，token 与组件映射以 `design-system.md` 为准，React 实现细节用 `components.md`，单文件交互交付物用 `artifacts.md`；不要在多个文档里维护冲突事实

## 信息几何表

结构先于风格。先判断内容关系，再选布局；不要把"页面"自动翻译成 Hero + 卡片网格，也不要把"应用"自动翻译成侧栏 + 仪表盘。

| 内容关系或任务 | 优先考虑的结构 |
|---|---|
| 连续阅读、论述、说明 | 文档流、章节、宽窄栏交替 |
| 同类对象快速扫描 | 列表、紧凑行、分组索引、feed |
| 多属性比较 | 表格、矩阵、对齐标尺 |
| 浏览后查看详情 | 主从视图、列表—详情、Miller 列 |
| 创建或直接操纵对象 | 画布 + 检查器、舞台 + 工具带 |
| 时间、版本、过程 | 时间线、轨道、步骤流、事件日志 |
| 空间或位置关系 | 地图、平面、节点图、空间叠层 |
| 状态推进或责任流转 | 看板、泳道、队列 |
| 深层层级 | 树、目录、outline、逐级钻取 |
| 少量重点内容的沉浸表达 | 舞台、蒙太奇、叙事滚动 |
| 多源监控与告警 | 分区仪表盘、主指标 + 明细流 |
| 输入与决策 | 单页表单、分组表单、向导、分支流程 |
| 高频命令与批量操作 | 命令面、工具栏、快捷键层、批处理表格 |

可以混合结构，但每种结构必须对应一种真实关系；内容关系没变就不要为了制造视觉变化而每屏换布局。

## 设计坐标与立场

结构确定后再定视觉。用一行可执行的坐标替代"像 A 撞 A"式描述：

> `[密度]` + `[几何]` + `[调性]` + `[材质]`，为 `[任务]` 优化，通过 `[签名手段]` 建立识别。

| 轴 | 可选方向 |
|---|---|
| 密度 | 稀疏聚焦 / 均衡 / 紧凑专业 |
| 几何 | 连续文档 / 列表矩阵 / 分屏工作区 / 空间画布 / 模块分区 |
| 调性 | 克制理性 / 温暖可信 / 编辑表现 / 活泼直接 / 工业精确 |
| 材质 | 扁平排版 / 线框结构 / 色块分区 / 分层表面 / 真实纹理 |
| 动效 | 近乎静止 / 反馈主导 / 空间转场 / 单一编排时刻 |

两个方向只在颜色或圆角上不同，就不是两个方向。立场一句话：

> `[特质]`，通过 `[结构/排版/色彩/动效手段]` 服务 `[用户任务]`，避免 `[不适合该产品的气质]`。

风格名称不是推理：说"高级、现代、极简、赛博"不等于作出决定，每个形容词都要落到可观察的结构或行为。

## 方向发散与选择

新项目或结构不明确时，先提出 2–3 个**结构上不同**的方向——改变阅读路径、密度、导航或操作位置，而不只是换颜色、字体和圆角。用六个维度比较并记录为什么选它、为什么放弃其余：

1. 首要任务完成速度
2. 信息扫描与比较效率
3. 内容增长后的稳定性
4. 平台与输入方式适配
5. 无障碍与极端状态
6. 品牌辨识度与实现成本

现有产品、明确 brief 或成熟设计系统已经给出结构时，不要为了展示发散而强行生成多个方案。

## 把响应式当作重组

不要把桌面稿等比缩小，也不要默认把所有列纵向堆叠。对每个宽度状态明确：

- 什么必须持续可见
- 什么可以合并、移入抽屉或按需显示
- 比较关系在窄屏如何保留
- 主操作如何保持可达
- 密度、导航与输入方式如何变化

断点依据是内容开始失效的位置；设备宽度只是测试样本。
