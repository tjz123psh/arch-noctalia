# Mobile Motion

动效为信息服务，不为炫技。每段动效必须回答一个问题：发生了什么、对象去了哪里、系统是否收到操作、内容之间是什么关系。答不上来的动效删掉。移动端还多两条硬约束：**动效运行在对手指负责的进程里**（手势必须能打断它），以及**它可能跑在低端设备或电量受限模式下**。

## 动效准入

先默认没有动效，再逐条论证加入。加之前回答三问：

- 它解释了哪一个状态变化、空间关系或因果反馈？
- 去掉它，用户是否会失去对界面的理解或掌控感？
- 它是否复用界面已有的空间逻辑（元素从它来的地方进、回它去的地方出）？

三个都答不上来就是装饰，删。**最强的"AI 味"来自反射式统一入场**：给每屏每个区块套同一条淡入上移。移动端还有一个更常见的替代品：给每个列表项套同一条 stagger 延迟。两者都是缺省，不是设计。

入场动效只播一次，播完界面就静止——**只有入场的界面截一张静态图就是死的**。要判断静止态是否成立：截图去掉一次性动画后，界面是否还有层级、有氛围、有在场感。

## 时长与缓动语义

时长按"移动距离与元素尺寸"选，不拍脑袋：

| 类型 | 时长 | 缓动 |
|---|---|---|
| 点击反馈（高亮、涟漪、开关） | ≤ 100ms | linear / ease-out |
| 小元素状态变化（颜色、图标、chip） | 150-200ms | ease-out |
| 局部转场（sheet、drawer、展开折叠） | 200-300ms | ease-in-out / standard |
| 全屏转场（页面、模态、导航栈） | 300-400ms | 平台标准曲线 |
| 大幅编排时刻（品牌入场、构造演示） | 按内容定，可更长但必须可跳过 | 定制曲线 |

缓动语义：**进场用 ease-out**（快起慢停，元素"落位"），**退场用 ease-in**（慢起快走，元素"离开"），位移用 ease-in-out。进场用 ease-in 显迟钝，退场用 ease-out 显拖沓。

平台原生语言（细节见 `ios.md` / `android.md` 的动效小节）：

- **iOS**：默认弹簧，带轻微回弹，约 0.3-0.4s；用 `UIViewPropertyAnimator` / SwiftUI spring 的 damping 与 response 语义，不要硬套线性时长。
- **Android**：Standard `cubic-bezier(0.4,0,0.2,1)`、Emphasized `cubic-bezier(0.2,0,0,1)`；优先 `MaterialTheme.motionScheme` 的 spring token，不硬编码 `tween`；Material 3 的 spatial spring（可回弹）用于位移与缩放，effects spring（临界阻尼）用于颜色与透明度。
- 两端都**不要跨平台硬搬**另一端的动效语言；同一 App 内动效曲线也必须一致。

## 手势连续性与可中断转场

这是移动端相对桌面的关键差异：**转场由手指驱动，不能被锁成固定时长动画**。

- **跟手**：滑动关闭 sheet / 返回上一页时，位移与缩放实时映射手指位置（进度 0→1），松手时按当前速度与位置决定"接续完成"还是"回退"，而不是回到起点重播。
- **可中断、可反向**：动画进行中再次触摸或反向滑动，必须从当前位置与当前速度平滑接管。iOS 交互式转场用 `UIPercentDrivenInteractiveTransition`，Android 用 prediction + 共享轴，RN 用 Reanimated 的 `Gesture` + `withSpring`，而不是 `Animated.timing` 播放固定序列。
- **速度延续**：松手瞬间的速度要传给弹簧 / 缓动，避免"手指在动、元素已停"的割裂感。
- **边界要有物理反馈**：越界拖拽时阻尼跟随（橡皮筋），松手回弹；不要硬截断在边界。
- **触感与动效对齐**：长按触发、拖拽吸附、下拉刷新阈值、开关切换这些时刻的 haptic 应与动画起点对齐，早于或晚于视觉都会显得廉价。
- 手势驱动的转场必须与系统手势协作：不与边缘返回、下拉通知栏、多任务手势抢同一片区域（见 `gestures.md`）。

## 编排

- 一个界面同时最多一个"主编排时刻"，其余保持克制；力度花在一处。
- 列表逐项出现（stagger）是合法的，前提是每项延迟很小（20-50ms）且总时长可控；不要把它当成每个列表的默认。
- 关联元素共享一条时间线（源—目标 morph、共享元素转场、容器变换），而不是各自独立动画。
- 动效增强一个**已经可见的默认态**：不要把内容可见性绑在动画回调上，否则动画被跳过时内容整块缺失。
- 展开 / 折叠优先用容器变换（卡片扩展为详情页），而不是把内容淡入淡出——空间连续性本身就是信息。

## 性能预算

- 只动 `transform` 与 `opacity`（合成器层）；宽高、`top`/`left`、`margin`、`shadow` 的动画会掉帧。
- 移动端基准是**低端设备**，不是旗舰：目标 60fps，掉帧的动效不如没有；RN 上用 `useNativeDriver` 或 Reanimated 的 worklet 跑在 UI 线程，避免 JS 线程卡顿导致动画撕裂。
- 高级材质（blur、backdrop-filter、mask、阴影泛光）可以进调色板，但代价高，先在低端设备验证。
- 动画不能阻塞交互：转场期间滚动、返回、键盘仍要响应。
- 持续监测：长列表滚动、图片流、连续转场时看帧率与内存，避免动画造成的泄漏。
- 详见 `performance.md` 的动画性能小节。

## reduced-motion 降级

`prefers-reduced-motion: reduce`、iOS `UIAccessibility.isReduceMotionEnabled`、Android `ANIMATOR_DURATION_SCALE=0` 都不是可选项。每段动效都要有替代：

- 位移 / 缩放 / 旋转 / 视差 → 退化为交叉淡入或即时切换。
- 自动播放、循环、大幅编排、环境微动 → 关闭或降为静态氛围。
- 手势驱动的转场 → 立即切换到位，但仍保留手势功能本身（不要顺手禁掉返回手势）。
- 降低透明度 / 减弱动效（Reduce Transparency）下，玻璃与模糊材质的对比度要仍然达标。
- 降级后内容必须完全可见、可用，不残留半截动画或空白。
- 反过来，**关闭动效不等于可以没有状态反馈**：pressed、loading、成功 / 失败仍然要即时可见，只是不再有位移。

## 自检

- 是否给每个区块 / 每个列表套了同一条入场动画？（最强 AI 味信号）
- 入场播完后截一张静态图，界面是活的还是死的？展示 / 品牌 / 沉浸型界面若静止态毫无持续元素，是欠交付而非克制。
- 转场能否被手指打断并从当前位置接续？还是播放固定时长动画、松手就失控？
- 每段动效能否说出它承载的信息？说不出就删。
- 动画是否只动 transform / opacity，是否在低端设备或电量受限模式下验证过 60fps？
- reduced-motion 下每段动效是否都有可见、可用的替代，且交互功能没有被一并移除？
- 动效曲线与时长是否贴合目标平台原生语言，且两端实现一致？
