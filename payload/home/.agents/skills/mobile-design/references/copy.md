# Mobile Copy：文案与措辞

移动端每条文案都占用稀缺的小屏空间，还常被读在走动、单手、被打断的场景里。它和间距、颜色一样是设计材料，不是装饰。

**触发时机**：写按钮、标签、错误消息、空状态、权限说明、系统弹窗文案，或做文案诊断时读本篇。表单错误体系见 `forms.md`，空状态与引导策略见 `onboarding.md`，品牌语气基线见 `critique.md` 的品牌切面。

## 短文案约束

| 元素 | 长度上限 | 说明 |
|---|---|---|
| 按钮 | 2–4 个汉字 / 1–2 个词 | 超了改词，不要缩字号 |
| Tab 标签 | 4–6 个字符（含图标） | 5 个 Tab 是上限，标签再长就挤 |
| 导航标题 | 1 行，约 20 字符内 | 过长截断并保留完整可查路径 |
| 列表行标题与副标题 | 标题 1 行，副标题 1–2 行 | 截断必须有展开或详情路径 |
| Toast / Snackbar | 1 行，≤ 20 字 | 再长用内联消息或底部 sheet |
| 字段标签 | 完整词，2–6 字 | 格式信息放示例，不塞进标签 |

统一规则：**文案优先级低于布局**——小屏放不下时改文案，不改字号、不缩触摸目标；少于 11pt / 12sp 的文字属于不合格（见 `SKILL.md` 第一段）。中英混排按实际渲染宽度算，不按字符数算。

## 从 Web 诊断表适配

Web 的病灶在移动端同样成立，但改法要按小屏与触屏调整：

| 病灶 | 移动端表现 | 改法 |
|---|---|---|
| 术语 | 「同步 Webhook 配置」塞进设置行 | 换用户自己的说法：「通知设置」 |
| 歧义 | 对话框里成对的「确定 / 取消」 | 动词 + 对象：「删除照片」「保留」 |
| 被动语态 | 「文件已被上传」 | 「已上传」或「我们已上传你的文件」 |
| 冗长或过简 | 错误消息写了半屏，或只写「错误」 | 保留动作与结果，删填充；其余移入详情页 / 帮助 |
| 假设用户已知 | 「启用双因素」不给路径 | 补一句为什么、在哪做 |
| 缺上下文 | 只报失败 | 原因 + 可执行动作（见 `resilience.md`）；语气跟随用户当下状态，报错克制、成功一句 |
| 格式信息塞标签 | 标签写「手机号（11 位，不含 +86）」 | 标签「手机号」+ 占位示例 + 键盘类型 |

## 按钮、动作与破坏性确认

- 写具体动词 + 对象：「保存修改」「加入购物车」，不用「提交」「确定」「是」。
- **全程同名**：按钮写「发布」，Toast 就说「已发布」；登录页、标题、按钮都叫「登录」。
- 破坏性动作的确认必须写明**对象与影响范围**：「删除「报表」？删除后团队成员都将失去访问权限。」不要写「确定要删除吗？」
- 有撤销窗口的删除用轻量确认或直接执行 + 撤销（见 `gestures.md`），不要叠两层确认；影响面大且不可逆（注销账号、清除全部数据）用**输入确认**（输入对象名或「删除」），而不是普通对话框。
- 按钮顺序与颜色按平台惯例（iOS 用 `destructive` 红色），危险动作不放默认高亮；下滑 / 返回手势不能变成默认「确认」。
- 底部 sheet 的关闭写「关闭」或走平台手势，不写「返回」；加载中保留原文案或改为进行时（「发布中…」），不要换成无信息的「请稍候」。

## 错误消息

结构固定三段：**发生了什么 → 为什么 → 怎么修**，且不要归咎用户。

| 场景 | 别写 | 改写 |
|---|---|---|
| 校验失败 | 「输入无效」 | 「邮箱需要包含 @，例如 name@example.com」 |
| 网络失败 | 「网络错误」 | 「网络连接不稳定，请检查后重试」+ 重试按钮 |
| 无权限 | 「Error 403」 | 「你没有查看此内容的权限，请联系管理员开通」 |
| 服务端错误 | 堆栈或错误码 | 「服务暂时不可用，请稍后重试」+ 反馈入口 |

字段错误用内联消息 + 键盘旁可见（见 `forms.md`），**不要用 Toast 或系统弹窗报字段错误**；错误消息与字段标签共用同一套术语，不道歉、不含糊、不甩锅。

## 空状态文案

| 类型 | 结构 | 示例 |
|---|---|---|
| 首次使用 | 价值一句 + 主操作 | 「还没有收藏。看到想看的内容点收藏，这里就会留下它。」+「去逛逛」 |
| 用户清空 | 轻提示 + 重建路径 | 「已清空。想恢复可以从备份导入。」 |
| 无结果 | 说明原因 + 改查询 | 「没有匹配「咖啡」的结果。试试更短的关键词或清除筛选。」 |
| 无权限 | 原因 + 获取路径 | 「仅团队成员可见。请联系管理员邀请你加入。」 |
| 出错 | 失败 + 重试 | 「加载失败。请检查网络后重试。」+「重试」 |

禁止「暂无数据」「空空的」这类无信息量的默认文案，也不要在空状态里做广告。

## 权限与系统文案

- **应用内铺垫页**先讲清「为什么需要 + 用来做什么 + 不用会失去什么」，一两句后再触发系统弹窗。系统弹窗里用户只能看到应用名和 `Info.plist` / `AndroidManifest` 的那行说明，所以它必须**说出具体用途**：「用于扫描账单二维码」，不是「需要相机权限」。
- 权限说明必须本地化，缺失或空泛会导致审核驳回与拒绝率上升；拒绝后的引导写清具体路径：「前往「设置」→「隐私」→「相机」允许访问」，不要只说「请在设置中开启」。
- iOS 通知的 `provisional`（静默投递）不必先弹窗打扰，保持静默投递并在应用内给订阅开关（见 `onboarding.md`）——但**不要**因此长期不请求正式授权。

## 通知与系统级对话框

- **通知文案**：标题给「谁 / 什么」，正文给「发生了什么」，语气比界面更克制——不要营销腔，也不要用「你有一条新消息」这类无信息量文案；通知里说的事，点进来必须成立。
- **该用系统对话框**：权限请求、破坏性不可逆操作、iOS 评分请求（`SKStoreReviewController`，一年最多 3 次且不能强制弹出）。
- **该用自定义界面**：应用内的确认与选择（底部 Action Sheet 或应用内对话框），以及需要自定义布局或多选结构的确认。
- 不要用系统对话框做应用内表单和长文案，也不要用自定义弹窗伪装系统权限弹窗。**应用商店描述、更新日志与商店截图文案不属于界面文案**：不要在 App 内引用，也不要让商店文案承诺界面做不到的事。

## 多语言膨胀

同一句话翻到不同语言长度差异很大（德语、芬兰语通常需要更多空间，中文最紧凑），小屏最容易被撑破：

- 文案上限按**目标语言的最长版本**定，不按中文长度定；固定宽度的按钮、Tab、对话框按钮要逐语言真实渲染检查截断（方法见 `critique.md` 排版切面）。
- 不要用缩写硬压长度（「设置」不要缩成「设」）；留出膨胀余量或改结构（图标 + 短标签）。
- RTL 语言下方向与标点位置镜像，不能靠字符串拼接造句子；数字、日期、货币一律走系统格式化。本篇只讲文案层面，布局与 locale 格式化的完整处理按项目 i18n 方案执行。

## 自检

- 遮住界面只看文案，能否知道每屏要做什么？同一动作在各处是否同一个叫法？
- 按钮文案是动词 + 对象吗？破坏性确认是否写明对象与影响？
- 每条错误消息是否都说了原因和下一步？有没有甩锅或暴露错误码？
- 五类空状态的文案是否都给了下一步动作？
- 权限说明是否说了具体用途？最长语言版本下按钮、Tab、对话框是否仍放得下？
