# Mobile Design

移动端是独立媒介：屏幕小、单手持握、系统手势与安全区不由你决定、平台惯例优先于个人偏好。本 skill 端到端覆盖设计 → 实现 → 验收，按下方顺序推进，不要跳步。

## 工作流

1. **判断**（第 1 段）：平台（iOS / Android / 双端）、已知/推断/未知、一句话问题、信息架构与导航模型、内容模型、分组、密度与单手可达性、平台惯例、动效动机、权限与中断——逐项给结论
2. **UI Contract**：结构定下后、实现前把决定写成一句话加最小模板（见第 1 段的模板）；短任务写进对话（≤ 8 行），跨回合或多人协作落到项目根 `DESIGN.md`
3. **分流**（第 2 段）：按判定信号读一到三篇 reference，不追求全读
4. **实现**：跟随项目现有架构、命名与测试；平台惯例优先于个人偏好；只为明确的复杂度新增抽象或依赖；保持公开接口与配置默认兼容
5. **视觉闭环**：真实运行 → 截图 → 按 `references/critique.md` 自评 → 修正 → 再截图（视觉变化时必须走完）
6. **验收**（第 3 段）：选小改 / 常规 / 发布，逐维度留截图、录屏或日志证据，写出残余风险

范围窄的评审（单个页面、一处安全区问题、一次对比度修复）可从第 2 段直接开始，但仍要给出第 1 段中与本次改动相关的判断结论，并按第 3 段留证据。

## 一、判断（在此段直接决定，不读文件）

**先定平台，再定结构，最后定视觉。**

**证据分类**：**已知**取自需求、现有代码、真实数据与当前实现；**推断**是为推进所作的最小假设，说明依据并保持可逆；**未知**是会改变架构的问题，能从项目里发现就先发现，只有高影响且不可回退时才问用户。不要凭"典型 App 长这样"填补空白。

**一句话问题定义（写下再动手）**：为 `[谁]` 在 `[什么场景]` 完成 `[首要任务]`，需要突出 `[内容/操作]`，成功表现为 `[可观察结果]`；移动端还要写清输入方式（单手持握 / 双手 / 外接键盘）与主操作的单手可达位置。写不出这句话就先补信息，不要从组件库开始。六个变量决定取舍：使用频率、熟练度、紧迫性、错误代价、内容密度、设备与输入方式——高频消费界面与低频专业工具，不能用同一套简化逻辑。

**UI Contract（结构定下后、实现前写下）**：任务、截图评审与验收共用同一份交接物，不额外造设计文档；短任务写进对话（≤ 8 行）并在压缩上下文时原文保留，跨回合或多人协作落到项目根 `DESIGN.md`。

```text
任务：谁在什么环境完成什么；成功的可观察结果；主操作及其单手可达位置。
结构：导航模型、内容分组、主次动作与渐进披露。
立场：场景气质、一个服务任务的记忆点、要避免的失配语气。
令牌：颜色使用比例、动态文本样式、间距刻度、圆角、动效曲线与时长。
状态：加载 / 空 / 错误 / 离线 / 无权限 / 极端内容；键盘弹出与后台返回后的恢复。
形态：目标机型与系统版本、最小到最大屏、字号档位、横竖屏与折叠、平板是否重组。
验收：风险级别、设备与状态矩阵、要拿到的截图 / 录屏 / 日志。
```

纪律：每行只写能指导实现或验证的决定，未知项标"待验证"；"避免项"只针对当前 brief，不是跨产品禁令；项目已有设计系统或 brief 时链接权威来源，不要复制第二套 token。视觉评审发现问题先改实现，若推翻了原决定就同步更新 Contract。

**跨平台 vs 单平台**：目标只提 iOS 或 Android 时按单平台做，深挖该平台 reference；两端都要时用一套品牌视觉 + 两套导航与系统行为。品牌色、插画、内容布局可以统一；导航模式、返回行为、状态栏处理必须跟随各自平台，不要把一个平台的形态硬套到另一个。

**信息架构与导航模型**（按内容关系选，不按美观选容器）：

| 内容关系 | 导航模型 | 不要默认成 |
|---|---|---|
| 3-5 个同级高频目的地 | 底部 Tab Bar | 抽屉菜单藏核心内容 |
| 层级内容、逐级下钻 | Navigation Stack / Fragment Back Stack | 平铺平行入口 |
| 5+ 目的地、低频导航 | Drawer（Android 常见，iOS 慎用） | 塞进 Tab 变成拥挤图标栏 |
| 同级视图切换 | Segmented Control / Tabs | 新建一个页面栈 |
| 临时表单或选择 | Modal Sheet / Bottom Sheet | 整页跳转丢上下文 |
| 分步流程 | Wizard / Stepper | 单页堆满字段 |

导航模式全应用一致：有的页面用抽屉、有的用 Tab，是明确的错误。**返回行为**是平台契约——iOS 左上返回 + 左缘滑返，Android 系统返回 / 预测性返回；不要用应用内返回按钮替代系统返回，也不要用返回直接退出应用。Tab 层不承担下钻职责，下钻层不重新出现 Tab。

**内容模型与首要任务**：列出真实对象、属性、动作、关系、状态，再决定布局。每个界面只回答一个问题：用户来这里完成什么？据此定视觉焦点与首要动作，次要内容渐进披露。

| 任务关系 | 首选结构 |
|---|---|
| 扫描同类内容 | 连续列表、分组列表、feed（行优于逐条卡片） |
| 浏览后看详情 | 列表 → 详情栈，返回时恢复筛选与滚动位置 |
| 位置与附近 | 地图 + 可折叠结果层，双向联动 |
| 时间与活动 | 日程、时间线、事件流，不要打散成无序卡片 |
| 创作与直接操作 | 全屏画布 + 上下文工具，按选择出现 |
| 少量关键状态 | 聚焦摘要 + 详情流；仅在需同时监控时才做仪表盘 |
| 输入与决策 | 单页分组或分步，按认知负荷切分，不按字段数切分 |

卡片只用于有独立意义的对象边界；设置、消息、文件、事件这类同类内容，用行、分组与排版层级更高效。横向滚动不得藏核心内容。缩放桌面 IA 成单列、或用卡片列表替代内容建模，都不算移动端设计。

**分组靠关系，不靠容器**（先用最轻的手段建立关系，只有关系需要显式边界时才升级到容器）：

| 手段 | 机制 | 移动端何时首选 |
|---|---|---|
| 邻近律 | 空间接近 | 大多数分组；零视觉开销，**组内间距必须小于组间间距**，这个比例而非固定值创造层次 |
| 共同区域律 | 共享边界或背景 | 边界本身有含义时才用：可独立操作、可滑动、可选择的列表项卡片；sheet 内分节、表单分组 |
| 隔离效应 | 与周围形成差异 | 一屏只强调一处：唯一 filled 主按钮、当前选中态 |

- 标签贴紧自己的输入框，不贴紧下一个字段；分组标题离下方内容比离上一节更近；用一致的间距刻度（4/8/16/24/32）。
- 分组要落在触摸目标上：同一组操作的目标间隔 ≥ 8pt/dp，组内目标紧凑而组间留出足够空隙，避免"想点这个点到那个"；可滑动或长按的行本身就是一个分组单元。
- 安全区参与分组：安全区不能当成组间距——内容不贴状态栏 / 手势条，底部主操作所在的组要整体避开 Home Indicator 与系统手势热区。
- 小屏优先留白与对齐，其次通栏分隔线，最后才是描边卡片；**嵌套容器最多两层**，每层必须表达不同的层级或交互范围。
- 分组边界在深色模式、增大对比度与低端屏幕下都必须成立；分组不能只靠颜色，配合间距、形状或字重。
- 一屏多个同等强调的元素会互相抵消；强调会"通胀"——每加一处高亮，其他高亮就贬值，并要在 pressed / disabled / 灰度下仍可区分。
- 用户误读结构时，先查邻近关系与组内组间间距，通常根因在这里，而不是缺一条分隔线。

**密度与单手可达性**：拇指热区在屏幕下 1/3，主要动作放这里，顶部只放低频或危险动作；破坏性动作与主操作分开。基础网格 8pt/dp，页面边距 16pt/dp，列表行高 ≥ 48pt/dp，相邻触摸目标间距 ≥ 8pt/dp；触摸目标 iOS ≥ 44×44pt、Android ≥ 48×48dp；正文 iOS ≥ 16pt（标签 ≥ 11pt）、Android ≥ 16sp（标签 ≥ 12sp）。密度由"需要同时比较的量"决定，不由可用空间决定——紧凑不是把间距减半。

**字号层级**两端各自映射：iOS Large Title 34 / Title 28 / Headline 17 Semibold / Body 17 / Caption 12；Android Display Large 57 / Headline Large 32 / Title Large 22 / Body Large 16 / Body Small 12。用平台可缩放的文本样式，不硬编码固定字号与固定行高；最大缩放档位（AX5 / 200%）下不截断、不重叠。

**平台惯例优先于个人偏好**：系统返回、状态栏、安全区避让、文本选择、手势热区都遵循平台；违反惯例的"创新"要先有证据。安全区用平台 inset API，不硬编码坐标——iOS 避让刘海 / 灵动岛 / Home Indicator，Android 避让状态栏 / 导航栏 / 挖孔。

| 手势 | iOS | Android |
|---|---|---|
| 返回 | 左缘滑动 | 系统返回（左右缘 / 返回键） |
| 列表项滑动操作 | 原生标准（删除 / 标记） | 支持但不普遍 |
| 长按 | 上下文菜单 | 选择 / 多选 |
| 关闭模态 | 下滑 | 返回键 |
| 下拉刷新 / 双指缩放 | 支持 | 支持 |

屏幕上没有 hover：次要操作与状态反馈必须有触摸可达形态——足够大的可点区域、pressed 反馈、长按菜单或独立入口。只能靠滑动或长按才能完成、又不可发现的操作是设计缺口。模式选择、触摸反馈、滑动与长按规范见 `references/gestures.md`。

**动效动机**：动效只承载状态变化或空间关系，不做装饰。点击反馈 ≤ 100ms（iOS 高亮 / 变暗，Android 涟漪）；开关切换 200-300ms；页面转场 300-350ms；长按 500ms 触发上下文菜单或多选；滑动操作跟手显示动作按钮。iOS 用弹簧物理，Android 用缓动曲线（Standard `cubic-bezier(0.4,0,0.2,1)`，Emphasized `cubic-bezier(0.2,0,0,1)`）并优先 `MaterialTheme.motionScheme` 的 spring token，不硬编码 `tween`；动画速度与元素尺寸匹配——小组件用快、全屏转场用慢。**手势驱动的转场必须可中断**：跟手指移动、松手按速度接续或回退，不要锁成固定时长动画。纯装饰动画删掉；reduce motion 开启时降级为淡入或瞬时切换，不留半截动画。完整准入、时长缓动语义与性能预算见 `references/motion.md`。

**权限与中断是结构问题，不是实现细节**：权限在**用到的那一刻**、一次只问一个地请求，被拒要有降级路径与设置引导，永久拒绝要能恢复；断网 / 弱网 / 切网、后台被系统回收、来电打断、旋转与折叠、深链与推送进入都要有明确落点，冷启动要能恢复上次状态与未完成内容。这些属于 Contract 的「状态」行，判定与降级表见 `references/resilience.md`，首启的权限顺序与激活路径见 `references/onboarding.md`。

**启动前停止条件**：所有内容塞进同尺寸卡片；主操作不在可达区；导航模式前后不一致；违反系统返回或安全区；动效没有信息动机；加载 / 空 / 错误 / 无权限状态缺失；首启先连弹权限或讲完所有功能才让人用；把桌面界面压成一列。出现任一条先改结构，别进实现。

常用阅读顺序（避免一次全读）：

- **新做一个平台页面**：`android.md` 或 `ios.md` → 收尾读 `validation.md` 取证据组合。
- **双端统一改版**：`platform-differences.md` 定"统一 / 分治"清单 → 各读各平台篇 → `validation.md`。
- **修具体缺陷**：按症状直读——刘海与键盘问题看对应平台篇的安全区小节，长按 / 滑动 / 触摸反馈读 `gestures.md`，表单与输入读 `forms.md`，卡顿看 `performance.md`，读屏问题看 `accessibility.md`，验收漏项看 `validation.md`。
- **选型与依赖**：组件库 / 动画库 / 表单库 / 图标库读 `ui-libraries.md`；长列表、图片流、启动耗时读 `performance.md`。
- **交互模式没定**：读 `gestures.md` 的模式总览与决策树，先定模式和状态，再谈组件形态。
- **输入密集或表单被投诉**：读 `forms.md`（键盘类型与自动填充、校验时机、错误体系）。
- **动效被质疑（"太花"或"太平"）**：读 `motion.md`；把动效当护栏用，而不是当特效库用。
- **评审现有界面**：读 `critique.md` 选切面，按下面的截图闭环走。
- **可访问性判定**：先读 `accessibility.md`；需要 WCAG 条文级合规结论时按第四段转出。
- **首启、引导或空状态被投诉没人用**：读 `onboarding.md`（Aha、权限时机、五类空状态、渐进披露）。
- **弱网、权限被拒、进程被杀、深链进错页**：读 `resilience.md` 对应小节，再去 `validation.md` 取证。
- **文案要改或要诊断**：读 `copy.md`（短文案上限、按钮命名、错误与空状态文案、权限与通知文案）。

## 三、验收证据（本 skill 内闭环，不调外部测试 skill）

用真实设备或模拟器上的真实内容验收，**不接受单张设计稿或单一机型截图**。证据优先级：自动化测试（UI / 无障碍扫描）> 真机截图或录屏 > 日志 > 设计稿走查。每条"通过"都要能指向截图、录屏、日志或测试；拿不出证据就写未验证，不要写"看起来没问题"。

**视觉改动必须先走截图自评审闭环**（新建、重设计或任何可见的视觉变化都适用）：

1. **真实运行**：在模拟器或真机上跑起来，不用设计稿或组件预览代替。
2. **截图**：按风险取关键屏与关键状态，**覆盖目标平台两端**；涉及"对标某参照界面"时，参照物必须真实渲染后截图，不能用文字描述代替画面。
3. **评审**：对着截图按 `references/critique.md` 选切面（至少：层次、排版、色彩、构图、可供性），逐项写观察—问题—修复，不要只读代码或凭印象。
4. **修正**：改实现而不是改说辞；若问题推翻了结构决定，同步更新第一段的 Contract。
5. **再截图**：复跑同一批屏与状态，确认修复且没有引入新问题；两轮截图都保留。
6. **进平台验收**：闭环走完后，按下表的风险级别取设备与状态证据。

没有这一轮视觉证据，"看起来没问题"不算通过；评审中 `major` 未修的项，验收判 **FAIL**。

最小主路径必须走完：冷启动 → 首要任务 → 错误恢复 → 返回 → 切后台恢复。按风险分级选组合：

| 风险 | 必做证据 |
|---|---|
| 小改 | 主流尺寸功能路径 + 安全区 + 深色模式 |
| 常规 | + 小屏与大屏、最大字体缩放、键盘弹出与遮挡、空 / 加载 / 错误状态 |
| 发布 | + 设备矩阵代表机型、缺口机型、横竖屏与折叠态、手势与系统返回冲突、权限拒绝与恢复、弱网与后台恢复、TalkBack / VoiceOver 全路径、对比度检查 |

必查项（逐条对应证据）：

| 检查面 | 不通过的样子 |
|---|---|
| 设备矩阵 | 只测一个大屏旗舰；平板 / 折叠态拉伸放大而非重组布局 |
| 安全区与刘海 | 内容被状态栏、灵动岛、挖孔、Home Indicator 或圆角裁切；硬编码避让值 |
| 字号缩放 | 最大 Dynamic Type / 字体缩放下文字截断、重叠、主操作被挤出屏幕 |
| 键盘遮挡 | 输入框或主按钮被键盘盖住；内容不随键盘滚动 |
| 手势冲突 | 应用内手势撞上系统边缘返回、下拉通知栏、多任务手势；滑动操作无可见替代入口 |
| 权限流程 | 首屏一次性索要全部权限；拒绝后崩溃、死循环或无法恢复 |
| 弱网与后台恢复 | 无限 spinner 无重试；切后台返回、来电打断、进程被杀后数据丢失或重复 |
| 视觉与层次 | 入口点不明确、主操作被埋或与次操作同权重；对比度、间距、圆角偏离令牌；与竞品模板无差别（详见 `references/critique.md`） |

状态覆盖一个都不能缺：default / pressed / focused / loading / disabled / error / empty / offline / permission-denied。旋转、折叠展开、深浅色切换、字体变化、前后台往返后，列表滚动位置与选中态必须保持；深链、推送点击、分享进入要落在正确页面且导航栈合理。

取证工具：Xcode Accessibility Inspector、Android Accessibility Scanner、Layout Inspector、Espresso / XCTest、Compose Preview、真机录屏。自动化扫描只能替代对比度与标签类检查，**不能替代**真机手势、键盘、弱网与读屏实测。

结果判定：

- **PASS**：有截图 / 录屏 / 日志 / 自动化测试指向，且覆盖该风险的必做项。
- **FAIL**：观察到不符合预期的行为，附复现步骤与证据。
- **UNAVAILABLE**：设备、机型、账号、网络条件或工具缺失导致无法取证，必须显式写出，不得用"应该没问题"替代。

交付报告至少列出：设备与系统版本、屏幕尺寸、主题、字体档位、输入法、复现步骤、证据、期望、实际、残余风险。完整设备矩阵、逐条检查清单与发布前 checklist 见 `references/validation.md`。

验收执行要点：

- **先定矩阵再测**，不要边测边加机型；矩阵由风险决定，改布局加机型，改行为加状态与生命周期路径。
- **用真实内容**：超长标题、多语言（CJK / 长德语词 / RTL）、数字极值、真实图片尺寸，不用 lorem 与占位图。
- **变更后可回归**：本次改动路径 + 相邻边界（返回栈、滚动位置、选中态、已填表单）都要重跑。
- **不隐藏失败**：缺设备、缺账号、缺网络环境都记 `UNAVAILABLE` 并写清阻塞原因，不要用"看起来没问题"结案。

## 四、跨端边界

- Do NOT 用于 Web 或网页应用、后台、仪表盘 → 用 `web-ui-design`。
- Do NOT 用于终端 TUI / CLI 全屏工具、picker、monitor → 用 `tui-design`。
- Do NOT 用于桌面原生界面（GTK / WinUI / macOS）→ 用对应桌面平台 skill。
- 本 skill 是移动端的**唯一端到端入口**：结构、视觉、交互、表单、动效、无障碍与验收都在本目录内闭环，不要再串第二个设计或测试 skill。宽泛或模糊的"做个 App"请求也从第一段开始：先写一句话问题定义与 UI Contract，再进入结构与平台落地。
- 动效准入、时长语义、编排与性能预算的完整方法论在 `references/motion.md`；交互模式选择与触摸反馈规范在 `references/gestures.md`；表单与校验体系在 `references/forms.md`；逐屏评审切面与输出格式在 `references/critique.md`；失败与权限的降级设计在 `references/resilience.md`；首启与激活策略在 `references/onboarding.md`；文案标准与诊断在 `references/copy.md`。
- WCAG 条文级合规审计不在本 skill 范围；本 skill 的 `references/accessibility.md` 是移动端落地清单，可支撑审计取证，但不替代合规结论。
- 纯后端 API、数据层或非视觉逻辑改动不走本 skill；只改一个明确样式值或修一个明确 UI bug 时，可直接读对应 reference，不必走完整流程。
- 响应式 Web 的移动端断点属于 Web 范畴，不属于移动 App；两者不要混用验收标准。
- 平板 / 折叠屏在本 skill 范围内（要求重组布局而非拉伸）；跨设备连续性（手机 → 手表 / TV / 车机）需在目标平台各自的 skill 中另行判断。
