# 跨领域示例：迁移思路，不复制结论

例 1 是本技能起点案例的抽象；例 2—6 是教学假想场景，不是已经做过的实验或事实结论。每次使用都必须重新核对当前对象、规则和授权。

## 例 1｜短暂异常：内部退场了，外部规则仍在作用

现象：一个对象开始／结束的瞬间出现异常，稳定后正常。各部分看起来不同步。

容易走错的路：直接归咎底层、缓存、硬件或并发；为了排除问题关闭全部功能；写出候选补丁就报告修好。

分析方式：

1. 核对真实运行对象、实际版本及当前覆盖规则，而非套用同名系统的旧架构。
2. 区分内容本身和外部附加效果的所有者，分别记录它们的开始／结束状态。
3. 检查撤销内部偏好后，外部是否重新启用默认或强制规则。
4. 比较“明确空状态”与“撤回偏好”，不要假定它们等价。
5. 用尽量不包含被怀疑机制的最小模型检验：保留对象不动，只切换这一处状态表达。
6. 再在真实使用路径确认，不能停在模型或编译结果。

迁移出的思想：异常可能来自两个组件各自合理的行为组合，不一定某个组件单独坏了。同步地传递错误语义，也能产生“不同步”的外观。

改进工作顺序：已有低风险配置对照时，应先考虑它，而不是立刻投入完整重建。明确“已制作候选”与“当前实际生效”的区别。对照背景变化时披露限制，不能伪装成严格单变量实验。

## 例 2｜数据报表：月末有差异，日常样本都正常

现象：某个汇总在月末错一点，原始行数看起来正确。

竞争假设：

- 日期边界／时区解释不同。
- 空白、零值、缺失值被不同步骤重新解释。
- 导出的报表仍使用旧数据范围或缓存，而非计算本身错误。

真实链：原始记录 → 类型转换 → 时间边界与过滤 → 聚合 → 导出 → 接收方打开。

最小检查：冻结少量手工可核算的记录，覆盖边界前后、空白与零；逐段核对去向，最后打开实际交付文件。先区分过滤、计算与交付版本，不重写整个分析管线。

需要问用户的决策：若业务口径未定，缺失数据算作零还是排除？统计日按哪个已认可的业务时区？能查到的制度先查，不把口径选择默默藏进公式。

验收：不仅公式结果正确，接收方使用的文件、范围和日期口径也正确。

## 例 3｜跨部门流程：显示审批通过，但执行方仍按旧规则做

现象：申请已“完成”，下游仍拒绝执行或继续旧流程。

竞争假设：规则本身无效；传播未完成；下游使用不同版本；撤销旧覆盖后恢复了另一条默认规则。

真实链：提交 → 审核 → 获批 → 发布 → 通知／同步 → 一线读取 → 实际执行。

最小检查：追踪一个获授权的代表性事项，记录每个交接点的状态含义、时间和实际读取来源。先查记录或做安全模拟，不拿真实权益、客户资金或审批边界随意试错。

追问重点：谁有权定义“完成”？谁承担执行风险？一个交接未完成时，允许的安全默认行为是什么？

最小处理可能是明确交接确认或修正发布状态，而不是更换整套管理体系。

## 例 4｜文档交付：作者预览正常，接收方打开错位

现象：内容看似已经制作成功，接收方仍看到缺字、分页或布局变化。

竞争假设：排版本身有问题；预览和导出路径不同；字体／样式依赖未随产物交付；接收方拿到旧文件。

真实链：编辑源 → 本地预览 → 导出 → 文件交付 → 接收方软件解析 → 实际显示。

最小检查：先核对实际送达的文件身份，再用能覆盖异常的少量页面和目标阅读环境检查；必要时制作一个只保留关键字体、表格或分页条件的样本。

追问重点：可编辑性和跨环境外观一致性哪个优先？允许附带哪些依赖？接收方真正使用什么格式？

验收：不能只以源文件预览或“导出命令成功”作为完成证据。需要确认交付文件在约定消费环境中的结果。

## 例 5｜产品／运营：总体数据上涨，少数用户却更难完成任务

现象：总体指标与真实抱怨冲突，别人使用很好，但某类条件下总失败。

竞争假设：个别使用差异；样本选择或统计口径变化；分群被总体平均掩盖；某个默认／例外规则只影响少数路径。

真实链：用户进入 → 分群或路由规则 → 实际经历的流程 → 行为记录 → 指标定义 → 汇总解释。

最小检查：使用合法可访问、脱敏且可比较的数据，按关键条件分群，并核对失败用户实际走过的路径。前后群体、时间或入口不同，不得直接把变化归因于改版。

追问重点：成功指标是否覆盖被牺牲的人群？多大改善值得多大损失？谁有权同意试验？是否有只读或更低风险的替代？

验收：既看总体，也看原先失败的代表性路径；不使用“多数人好评”否定局部事实。

## 例 6｜计划与个人工作：每一步看似合理，整体却总是延期

现象：任务清单很细，执行仍反复卡住；尚无明确技术故障。

竞争假设：估时偏差；前置依赖遗漏；交接状态含糊；计划依赖用户没有同意的取舍；资源在关键时段不可用。

决策树示例：

~~~text
交付目标与不可牺牲项
├─ 哪个截止时间是真约束？
├─ 哪些输入／批准必须先到？
│  └─ 缺失时采用什么获准替代？
└─ 范围、时间、质量冲突时，谁决定取舍？
~~~

先查现有日历、任务记录或资源条件；用户独有优先级和可接受代价再提问。一轮只讨论当前能够决定的分支。

最小检查可以是一次桌面推演：用一个具体交付项，从开始推到接收方验收，逐步检查前置条件和状态交接。推演能暴露依赖，不能证明未来执行一定成功。

交付：共享理解、风险清单和下一步执行决定是有价值的结果；若用户只要求审计划，不得把讨论自动升级为替他发信、调整日程或执行计划。

## 迁移时始终保留的五个问题

1. 真正被使用的对象是什么？
2. 哪个边界改变了状态的含义或可见时间？
3. 哪个强替代解释尚未排除？
4. 下一项最小检查会怎样改变行动？
5. 结果只存在于我的说明里，还是已经到达约定的使用与验收位置？
