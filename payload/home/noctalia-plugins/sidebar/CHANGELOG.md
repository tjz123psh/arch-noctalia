## Sidebar 2.4.4（热点客户端「连上但没网」：与 Docker 共存，2026-10-11）

现象：手机连上热点、拿到 10.42.0.25，但上不了网。

根因（靠 nftables 规则链与计数定位）：装了 Docker 的机器上，Docker 把 nftables 的 **FORWARD 基链策略设成 drop**；
NetworkManager 的 shared 模式虽然在自己的表（nm-shared-wlp3s0）里 accept 了 10.42.0.0/24，但 nftables 里 accept
不是跨基链的最终裁决 —— 包随后被 Docker 那条 drop 吃掉。手工加两条放行规则后手机流量立刻开始转发
（计数 0 → 2757 包 / 1.65 MB），根因确认。

修法（都在 rice-hotspot 与安装器侧；插件本体无逻辑改动，版本号一起走）：

- 新增 root 助手 /usr/local/bin/rice-hotspot-net：只做「往 DOCKER-USER 链放行/撤销 10.42.0.0/24 @ 网卡」，
  参数白名单校验；没有 DOCKER-USER（没装/没跑 Docker）时直接退出，零副作用。
- 新增 /etc/sudoers.d/rice-hotspot：只放行这一个 root 助手（NOPASSWD），其它操作照旧要密码。
- rice-hotspot：起完热点自动放行；`on` 在「配置一致」的空转路径上也幂等补一次（Docker 重启会清 DOCKER-USER）；
  `off` 时撤销；拿不到 root 权限时明确提示手动补一次，不静默糊过去。
- 安装器：两个文件进 files.tsv（755 / 440 root:root）；07 步部署前用 visudo -cf 预检，语法不合法直接中止
  （避免把 sudo 写坏）；tools/selfcheck.sh 加了同一道校验。

## Sidebar 2.4.3（热点「改了设置不生效」的根因修复，2026-10-11）

用户实测：在设置页改了名字，手机搜到的还是老名字。查下来是三个真 bug 叠在一起：

- **正在跑的热点从不应用新设置**：`rice-hotspot on` 原来看到「已经开着」就直接返回，改过的 SSID/密码/频段永远不生效。
  现在 `on` 是**收敛**语义：配置一致 → 空转；不一致 → 停掉旧热点、按新值重建再拉起（停之前记下旧值，失败尽量回滚）。
- **面板没有「应用」入口**：设置改了但热点在跑时，按钮只显示「关闭」，点下去反而把热点关了，看不出「还没生效」。
  现在按钮三态：未开启 →「开启」；开着但设置有变 →「热点 <SSID> · 待应用」+「应用」；正常 →「关闭」。
- **命令被宿主超时杀掉**：5G 起不来时 NetworkManager 要等约 26 秒才报错，同步等待会撞上宿主的命令超时
  （实测被 SIGTERM，退出码 143），留下半套配置。现在：插件改成**分离运行、不等输出**，靠轮询 state 收尾；
  脚本单次拉起加 12 秒上限并取消没起来的激活 —— 整条命令从约 31 秒压到约 14 秒。

另外两处加固：

- **本机 5GHz AP 起不来**（rtw89 / RTL8852BE，报「802.1X 请求方验证时间过长」，连试 3 次）：脚本自动回落到 2.4GHz，
  面板上标出实际频段（热点 tjzpsh · 2.4G），tooltip 说明回落原因；频段设置保留给能用的网卡。
- flock 并发锁：面板 / 命令行 / IPC 同时来两下时，第二个明确报「上一次热点操作还在进行」，不再互相打架。
- 新增 IPC（与面板按钮同一条代码路径，可挂 niri 键位）：
  noctalia msg plugin pang/sidebar:panel all hotspot on|off|toggle|status

验收：设置里改名 → 面板显示「待应用」→ 触发应用 → 2 秒内 NM profile 改名、约 14 秒内 2.4G 热点起来；
状态回到 on|tjzpsh|wlp3s0|10.42.0.1/24|tjzpsh|0|bg（pending=0）；离线回归与宿主静态检查 0 error / 0 warning。

## Sidebar 2.1.1（2026-10-08）

2.1.0 上线当晚发现"面板能打开、点击全无反应、且应用列表卡在'正在读取应用列表…'"的事故，本版为修复。

### 根因

- 宿主（Noctalia 5.2.1）每次脚本回调限 25 ms CPU；连续 3 次超时（或 60 s 内累计 5 次）会**自动停用整个插件运行时**（仅弹一次通知），此后点击、帧回调、IPC 全部被静默丢弃——表现即"点击无反应、列表永远加载中"，重开面板只显示停用前缓存的旧画面。
- 触发点是应用列表 / 最近文件的解析回调：本机宿主 Lua 环境中 `(.-)` 懒惰匹配代价异常高（90 行桌面文件解析约 13 ms），贴着预算上限；开机等负载场景下越线，连续超时触发停用。

### 修复

- 应用列表解析：`^(.-)\t...` 七段懒惰捕获 → `^([^\t]*)\t...` 字符类捕获（无回溯），90 行解析约 13 ms → 2 ms（实机测量）。
- 最近文件：`xmlUnescape` / `artDecode` 增加无 `&` / 无 `%` 快速路径（跳过 gsub 链）；刷新周期 10 s → 30 s。
- 行为不变：字段语义、XDG 优先级去重、隐藏/覆盖规则、排序与展示与 2.1.0 完全一致。

### 验证（2026-10-08）

- 全量离线测试与宿主 `noctalia plugins lint sidebar`（0 errors / 0 warnings）通过；改动仅上述 4 处。
- 实机：热重载后应用列表 53 项正常，媒体/窗口/最近文件加载正常；6 次快速开关压力测试 0 超时；IPC 派发返回 `ok: dispatched`。

### 已知限制与后续方向

Noctalia 5.2.1 的 [render 绑定](https://github.com/noctalia-dev/noctalia/blob/6ef43e2bf2f3d5b4205ec72a72e34a2ab76ce3b4/src/scripting/plugin_bindings.cpp#L473-L584) 每次转换整个描述树，但 [原生协调器](https://github.com/noctalia-dev/noctalia/blob/6ef43e2bf2f3d5b4205ec72a72e34a2ab76ce3b4/src/ui/ui_tree_reconciler.cpp#L752-L861) 会按 type/key 重用控件；缓存 Lua 表不等于避免宿主布局。面板关闭后重新打开仍会由宿主重建原生树。

[ScrollView](https://github.com/noctalia-dev/noctalia/blob/6ef43e2bf2f3d5b4205ec72a72e34a2ab76ce3b4/src/ui/controls/scroll_view.cpp#L442-L482) 高度变化会测量和排列正文，并可能因滚动条缩窄宽度。现有 API 没有通用的原生展开、clip-only、节点级更新或自然高度测量，柔和模式仍有这个宿主成本。默认轻量模式优先响应速度而不是长画卷效果；若仍敏感可选“关闭卡片动效”。

实际运行日志还显示 Noctalia 的 IconThemePollSource 约每分钟一次耗时 230–300 ms。这是整个宿主的周期性扫描，可能造成额外偶发停顿，不是本插件能够完全消除的。日志位置为 [noctalia.log](</home/pang/.cache/noctalia/noctalia.log>)；没有为了它修改宿主、系统权限或重启桌面。进一步解决需要单独确认宿主范围。

旧格式计时器兼容仍使用严格核验后的单 PID TERM，现有 shell/API 无法数学上消除核验到发信号之间极窄的 PID 复用窗口；新格式不发送信号。图片 MIME 校验不等同于完整图片解码验证。封面清理只针对本插件数据目录里匹配 sidebar-art-* 与旧版 art_N.jpg 的文件，不触碰其他插件或用户文件。
